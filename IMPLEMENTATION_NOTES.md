### 26. Bug Fix: Infinite Re-Render Loops from Unstable useEffect Dependencies

- **Root Cause:** Every `data.js` data access function (`get()`) calls `JSON.parse()` on localStorage data, which creates **new object/array references on every call**. When these unstable values are used as `useEffect` dependencies, the effect re-fires on every render, calling `setState()` which triggers another re-render → **infinite loop** → page freezes, all buttons become unresponsive.
  ```js
  // data.js:23-26 — every call = new reference
  function get(key) {
    const raw = localStorage.getItem(key);
    return raw ? JSON.parse(raw) : null;  // ← new object every call
  }
  ```
- **Affected files & fixes:**
  - `src/pages/bk/DetailSiswa.jsx:20-24` — `useEffect` depended on `[result]` (unstable object). Changed to `[result?.id]` (stable UUID string). Effect now only re-runs when the result ID actually changes.
  - `src/pages/siswa/Kuesioner.jsx:21-30` — `useEffect` depended on `[profile]` (unstable object). Changed to `[profile?.id]` (stable UUID string). Effect now only re-runs when the profile ID actually changes.
  - `src/pages/admin/ManajemenPengguna.jsx:16` — uses `[]` (mount only), safe.
  - `src/pages/admin/MasterNisn.jsx:16` — uses `[]` (mount only), safe.
- **Why it worked before the redesign:** It didn't — it was always broken, but the original simpler component trees rendered fast enough that React's 50-render limit wasn't hit in all cases. The redesign added more state updates and heavier renders, making the loops long enough to freeze the page observably.
- **Symptoms fixed:** "Kembali ke Beranda" button now works; all buttons remain clickable after every action; page no longer freezes; questionnaire submit flow completes correctly; BK notes save without freezing.

### Pages with explicit "Muat Ulang" refresh button
- **Beranda BK** (`src/pages/bk/Dashboard.jsx`) — refreshes all metrics, student list, and note counts
- **Daftar Siswa Bimbingan** (`src/pages/bk/DaftarSiswa.jsx`) — refreshes student table

- **Beranda Admin** (`src/pages/admin/Dashboard.jsx`) — refreshes user counts, student/parent tables
- **Manajemen Pengguna** (`src/pages/admin/ManajemenPengguna.jsx`) — refreshes user list
- **Data Master NISN** (`src/pages/admin/MasterNisn.jsx`) — refreshes master NISN list with kelompok data
- **Beranda Siswa** (`src/pages/siswa/Dashboard.jsx`) — refreshes kuesioner result, BK notes, and link code status

### Implementation pattern
Each page follows this pattern:
```jsx
const [loading, setLoading] = useState(true);
const [refreshing, setRefreshing] = useState(false);
const [lastUpdated, setLastUpdated] = useState(null);

const fetchData = useCallback(async (isRefresh) => {
  if (isRefresh) setRefreshing(true); else setLoading(true);
  try {
    // ... Supabase calls ...
    setLastUpdated(new Date());
  } catch (err) {
    console.error("fetchData error:", err.message);
  }
  if (isRefresh) setRefreshing(false); else setLoading(false);
}, [deps]);

useEffect(() => { fetchData(false); }, [fetchData]);
```

The refresh button:
```jsx
<button onClick={() => fetchData(true)} disabled={refreshing}
  className="inline-flex items-center gap-1.5 text-sm text-primary-medium hover:text-primary-dark disabled:text-gray-300 transition font-medium">
  <RefreshCw size={14} className={refreshing ? "animate-spin" : ""} />
  {refreshing ? "Memuat Ulang..." : "Muat Ulang"}
</button>
```

- `refreshing` is separate from `loading` so the page content stays visible during a refresh (only the button shows a spinner).
- `loading` is the initial mount state (`if (loading) return null`) to prevent rendering with empty data.
- Timestamps are formatted using `toLocaleString("id-ID", ...)` for Indonesian locale.

## 37. Student Deletion (Admin)

### Overview
Two destruction actions on the Manajemen Pengguna page, both protected by confirmation:
1. **Single student delete** — per-row "Hapus" button on siswa rows, with a confirmation modal.
2. **Bulk delete all students** — "Kosongkan Semua Data Siswa" red danger button with typed-word confirmation.

### Confirmation philosophy
**No delete executes on first click.** Every deletion action requires a two-step flow:
1. User clicks the action → a confirmation modal opens (the destructive action never fires yet).
2. Modal shows a clear warning in Indonesian, with "Batal" (safe default, secondary style) and "Ya, Hapus" (destructive, red).
3. Only clicking "Ya, Hapus" performs the deletion.

### Single student delete
- **File:** `src/pages/admin/ManajemenPengguna.jsx`
- **Trigger:** "Hapus" danger button on any siswa row's action column.
- **`handleDeleteClick(user)`** opens the modal by calling `getSiswaProfileByUserId(userId)` to get the student's nama and NISN, then sets `deleteConfirm` state with `{ userId, username, role: "siswa", nama_siswa, nisn }`.
- **Modal text:** "Apakah Anda yakin ingin menghapus siswa [nama] (NISN [nisn])? Tindakan ini permanen dan tidak dapat dibatalkan."
- **On confirm:** `handleDeleteConfirm()` calls `deleteStudentCompletely(userId)`.

### Bulk delete ("Kosongkan Semua Data Siswa")
- **Trigger:** Red danger button in the top toolbar area, labeled "Kosongkan Semua Data Siswa" with Trash2 icon.
- **Modal opens** with `showBulkDelete` state.
- **Modal text:** Warns that ALL students, results, BK notes, link codes, and parent accounts will be deleted. Admin/guru_bk/questions/master_nisn are preserved. NISNs return to available status.
- **Type-to-confirm:** An `<Input>` field requires the admin to type exactly `HAPUS`. The "Ya, Hapus Semua" button remains disabled until the text matches.
- **On confirm:** `handleBulkDelete()` calls `deleteAllStudents()`.

### Cascade deletion order (`deleteStudentCompletely` in `supabaseAuth.js`)
For a single student:
1. Query user row (verify role === "siswa")
2. Get siswa_profile for that user → siswaId, nisn, nama

6. `DELETE` kuesioner_results WHERE id_siswa = siswaId
7. `DELETE` link_codes WHERE id_siswa = siswaId
8. Find orang_tua_profiles linked to this siswa
9. `DELETE` users WHERE id = ortu.id_user (parent account)
10. `DELETE` orang_tua_profiles WHERE id = ortu.id
11. `DELETE` siswa_profiles WHERE id_user = studentUserId
12. `UPDATE` master_nisn SET is_claimed = false WHERE nisn = siswa.nisn
13. `DELETE` users WHERE id = studentUserId

For all students (batch operations using `.in()`):
1. `SELECT id FROM users WHERE role = 'siswa'` → studentUserIds
2. `SELECT id FROM siswa_profiles WHERE id_user IN studentUserIds` → siswaIds
3. `SELECT id FROM kuesioner_results WHERE id_siswa IN siswaIds` → resultIds
4. `DELETE` bk_notes WHERE id_result IN resultIds

6. `DELETE` kuesioner_responses WHERE id_siswa IN siswaIds
7. `DELETE` link_codes WHERE id_siswa IN siswaIds
8. `SELECT id, id_user FROM orang_tua_profiles WHERE id_siswa IN siswaIds` → ortuUserIds
9. `DELETE` users WHERE id IN ortuUserIds
10. `DELETE` orang_tua_profiles WHERE id IN ortuIds
11. `DELETE` siswa_profiles WHERE id_user IN studentUserIds
12. `DELETE` users WHERE id IN studentUserIds
13. `UPDATE` master_nisn SET is_claimed = false WHERE is_claimed = true (resets ALL claimed NISNs)

### 52. Fix logout — actually wire the handler (supersedes entry 50) (2026-06-28)

#### Problem

#### Root cause
In entry 50, `handleLogout` was changed to **only** call `logout()` (clear localStorage + `setUser(null)`), relying on two indirect redirect mechanisms:
1. A `useEffect` watching `user` → `navigate("/login")`
2. `ProtectedRoute` → `<Navigate to="/login" />`

Neither fired reliably after `setUser(null)`, so the user stayed on the protected page with the dropdown merely closed.

Additionally, `handleLogout` was defined **after** the early return `if (!user) return <>{children}<>`, meaning it was only available when `user` was non-null. While `handleLogout` is a plain function (not a hook), defining it after the early return is fragile.

#### Fix — `src/components/Layout.jsx`
- Moved `handleLogout` **before** the early return at line 159.
- Added `console.log("logout clicked")` at the top to confirm the handler fires.
- Changed redirect from indirect (`navigate` inside a `useEffect`) to **direct** `window.location.href = "/login"`:
  ```js
  const handleLogout = () => {
    console.log("logout clicked");
    try {
      logout();                       // clears localStorage + AuthContext state
    } catch (err) {
      console.error("Logout error:", err);
    }
    window.location.href = "/login";  // forces clean page load, all React state gone
  };
  ```
- `logout()` still runs first to clear `localStorage` (so the new page load finds no session).

- `navigate("/login")` from React Router requires the component tree to re-render with the new route. If `setUser(null)` doesn't propagate through all consumers before the next paint, the redirect may not take effect.

- No dependency on `useNavigate`, `ProtectedRoute`, or fallback `useEffect`s — the one line does what it says.

### 54. Fix profile dropdown menu items not executing (2026-06-28)

#### Problem
On desktop, clicking "Pengaturan Akun" or "Keluar (Logout)" in the profile dropdown only closed the menu — the action (navigate / logout) never ran. No console errors.

#### Root cause — `src/components/Layout.jsx` `ProfileDropdown`
The click-outside handler uses `mousedown` (line 122):
```js
document.addEventListener("mousedown", handleClickOutside);
```
React's `onClick` fires on the `click` event, which happens AFTER `mousedown`. The event sequence is:
1. `mousedown` on menu button -> bubbles to document -> `handleClickOutside` runs
2. `mouseup` on menu button
3. `click` on menu button -> React synthetic `onClick` fires

The `handleClickOutside` checks `!profileRef.current.contains(e.target)`. Although the menu button IS inside the ref's div, in practice with React's rendering (StrictMode, state batching), the ref tree may not contain the target at the moment `mousedown` fires, causing the menu to close. Once `setProfileOpen(false)` runs, React unmounts the dropdown, and the pending `mouseup`/`click` events find the target element removed from the DOM, so `onClick` never dispatches.

Additionally, even when the check works correctly, the order `setProfileOpen(false)` before the action (`navigate` / `logout`) means the menu visually disappears first, creating a race between React unmounting and the action executing.

#### Fix — 3 changes all in `ProfileDropdown` in `Layout.jsx`

1. **Stop `mousedown` propagation at the dropdown container** — added `onMouseDown={(e) => e.stopPropagation()}` on the `<div className="absolute right-0 ...">`. This prevents `mousedown` events from inside the dropdown from reaching the document listener. The outside handler only fires for clicks physically outside the dropdown.
2. **Reorder: action first, then close** — changed handlers from:
   ```js
   onClick={() => { setProfileOpen(false); navigate(...); }}
   ```
   to:
   ```js
   onClick={() => { navigate(...); setProfileOpen(false); }}
   ```
   Action executes first, menu closes second — no race condition.
3. **Added `console.log`** at the start of each handler for debugging.
